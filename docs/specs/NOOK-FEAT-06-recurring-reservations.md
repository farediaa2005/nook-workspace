# Architectural Specification: NOOK-FEAT-06 Recurring Reservations Engine

## 1. Executive Summary & Objective
NOOK Workspace manages educational halls and multipurpose meeting rooms for tutors, workshops, study groups, and corporate sessions. A significant portion of revenue stems from weekly or recurring academic tracks (e.g., "Physics Dr. Ahmed every Tuesday & Thursday from 16:00 to 18:00 for 8 weeks"). 

Currently, standalone reservations operate seamlessly, but modifying or canceling recurring series versus single occurrences requires formal, deterministic recurring series synchronization between Frontend and Backend. This specification provides the complete end-to-end design for recurring reservation series generation, conflict detection, single-occurrence exception management, and clean synchronization.

---

## 2. Domain Model & Recurrence Syntax

### 2.1 Recurrence Rule Standards (RFC 5545 iCalendar Aligned)
To avoid bespoke scheduling bugs, recurrence patterns conform to standard recurrence semantics:
- **Frequency (`FREQ`):** `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`.
- **Interval (`INTERVAL`):** Positive integer multiplier (e.g., `INTERVAL=1` for weekly, `INTERVAL=2` for every other week).
- **By Day (`BYDAY`):** Set of days of the week: `[0, 1, 2, 3, 4, 5, 6]` (0 = Sunday, 1 = Monday, ..., 6 = Saturday in JavaScript `Date.getDay()` convention).
- **End Condition:**
  - `UNTIL`: Terminal ISO date (e.g., `2026-12-31`).
  - `COUNT`: Finite number of occurrences (e.g., `totalSessions = 12`).
  - `ONGOING`: Indefinite rolling recurrence window up to 90 days ahead.

## 3. Conflict Detection Engine (High Performance O(N log N))

### 3.1 Interval Invariant
Given room $R$, any two reservations $A$ and $B$ conflict if and only if:
$$\text{Room}(A) = \text{Room}(B) \land \text{Date}(A) = \text{Date}(B) \land \max(Start_A, Start_B) < \min(End_A, End_B)$$

### 3.2 Self-Exclusion Rules
When editing an existing recurring series:
1. Occurrences generated by the series itself ($SeriesId = TargetSeriesId$) must **not** trigger self-conflicts against other occurrences in that same series.
2. Single-occurrence edits exclude only the specific instance being modified, while verifying non-overlap with both external bookings and neighboring occurrences within the series.

```typescript
export function checkSeriesProjectionConflicts(
  newSeries: RecurrenceRuleDto,
  timeFrom: string,
  timeTo: string,
  roomId: string,
  existingBookings: AdminReservation[],
  excludeSeriesId?: string
): { hasConflict: boolean; conflicts: { date: string; conflictingReservation: AdminReservation }[] } {
  const projectedDates = generateSeriesDates(newSeries);
  const conflicts: { date: string; conflictingReservation: AdminReservation }[] = [];

  for (const date of projectedDates) {
    const dayBookings = existingBookings.filter(b => 
      b.classroom === roomId || b.roomId === roomId
    ).filter(b => (b.occurrenceDate || b.fullDate) === date);

    for (const booking of dayBookings) {
      if (excludeSeriesId && (booking.reservationId === excludeSeriesId || booking.id.startsWith(excludeSeriesId))) {
        continue;
      }
      if (checkReservationOverlap(timeFrom, timeTo, booking.startTime, booking.endTime)) {
        conflicts.push({ date, conflictingReservation: booking });
      }
    }
  }

  return {
    hasConflict: conflicts.length > 0,
    conflicts
  };
}
```

## 4. Operational Workflows & UX State Transitions

### 4.1 Series Mutation Modal ("Apply to Single" vs "Apply to All Remaining")
When an operator drags, resizes, or edits an occurrence of a recurring series on the Timeline Grid:
1. Modal presents prompt in Arabic-first RTL:
   - **هذا الموعد فقط (This occurrence only):** Cancels the parent series on date $D$ via `DELETE /api/Reservations/{seriesId}/occurrences?date=YYYY-MM-DD`, and writes a new standalone reservation for date $D$ with updated timings.
   - **كل المواعيد القادمة (All future occurrences):** Splits the parent series: parent series terminal `endDate = D - 1 day`, and spawns a new series starting at date $D$ with updated schedule.
   - **كامل السلسلة من البداية (Entire series):** Updates parent series master record via `PUT /api/Reservations/{seriesId}`.

## 5. Backend REST API Endpoints Required

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/Reservations/series` | Create recurring series with `RecurrenceRuleDto` |
| `PUT` | `/api/Reservations/series/{id}` | Update entire recurring series definition |
| `POST` | `/api/Reservations/series/{id}/split` | Split series starting from specific date |
| `DELETE` | `/api/Reservations/series/{id}/cancel-day` | Exclude single date from recurring series (`canceledOccurrences`) |
| `POST` | `/api/Reservations/series/check-conflicts` | Validate recurring series projection across all dates before commit |

---

## 6. Frontend Resilience & Offline Fallback
- Series occurrences are calculated lazily up to 60 days in advance and rendered onto the timeline.
- Any manual single-date cancellation is optimistically added to `canceledDates` and cached in `localStorage` under `nook_series_cancels_{seriesId}` so that page reloads maintain accurate visual state even under network failure.
